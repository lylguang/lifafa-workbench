# 「每天一个GitHub热榜项目」文案结构优化方案

> 状态：方案稿，待用户确认后实施。
> 证据基线：2026-11-08 读取本机 `spoken-video` 工作区 34 篇已保存稿件（其中该账号 10 篇）、`analytics` 工作区的抖音采集指标、`publisher` 工作区的投递记录，以及本轮实地抓取的 GitHub Trending 页面与 5 份外部爆款方法论文档。
> 结论一句话：**这个账号的问题不是"写得不够好"，是"没有事实锚"**——写稿层拿不到 GitHub 的星数、仓库描述和今日新增，模型只能靠选题标题编，于是 10 篇稿件里 0 篇出现真实 star 数，`needsVerification` 中位数 4 条。

---

## 一、诊断：五条可证实的缺陷

### 缺陷 1（根因）：写稿层拿不到 GitHub 的真实数据

`spoken-video-content-store.mjs:974` 把信号传给写稿层时只拼了三个字段：

```js
payload: { source: signal.sourceId, text: `${signal.title}\n${signal.summary}${signal.url ? `\n${signal.url}` : ''}` }
```

而 `spoken-video-signal-adapters.mjs:419` 的 GitHub Trending 解析结果是：

| 字段 | 值 | 是否进入 `text` |
|---|---|---|
| `title` | `cloudflare/security-audit-skill` | 是 |
| `summary` | `An extremely fast... · JavaScript`（**仓库英文描述 + 语言**） | 是 |
| `hotValue` | `2548`（今日新增 star） | **否** |
| 总 star 数 | `65,243` | **否**（解析器根本没取） |
| forks | `4,236` | **否**（解析器根本没取） |

实测取一条真实信号拼出的 `text`：

```
cloudflare/security-audit-skill
An extremely fast Python linter and code formatter, written in Rust. · Rust
https://github.com/cloudflare/security-audit-skill
```

`包含 star 总数? false` / `包含今日新增? false` / `hotValue 出现在 text 里? false`。

**GitHub Trending 页面本身是有这些数的**（改造后用新解析器跑真实页面，2026-11-08 实抓，**15/15 条全部解析成功**）：

```
vercel-labs/agent-browser        总star 46,861   fork 3,211   今日 190
cloudflare/security-audit-skill  总star 65,790   fork 4,272   今日 2,085
google/skills                   总star 23,433   fork 1,957   今日 443
mattpocock/skills               总star 317,753  fork 26,582  今日 1,100
anthropics/skills               总star 188,822  fork 22,257  今日 390
```

15 条里总 star 与 fork 全部取到（15/15），无一条被 SVG `<path d="M8 .25a.75.75 ..."/>` 里的数字污染。

结论：**`hotValue` 被解析出来了，存在信号里，然后在拼 `text` 时被丢掉了**。账号定位里写着"star 数与增长趋势必须有数据支撑，不编造数据"，但写稿模型根本看不到这个数——它只能编，或者写"以官方为准"。

连带后果（实测 10 篇该账号稿件，归属按 `account.id` 判定——该账号改过名，「每天一个热门GitHub热榜推荐」→「每天一个GitHub热榜项目」，按名称筛会漏掉 6 篇旧名稿）：

- **0 / 10 篇**正文里出现真实 star 数（`54.6k star` 只出现在标题）
- **3 / 10 篇**的 `signals` 数组是**空的**，其中 2 篇 `sourceBoundary` 明写"本稿无信号素材输入；全部内容基于选题与通用公开认知展开，未引用任何具体 GitHub 仓库、star 数、发布说明或第三方数据"
- 其余 7 篇有信号，但信号来源全是**二手报道**（ai-daily-import 6 次、juejin/36kr/ithome/infoq/ifanr/baidu/toutiao/hacker-news 各 1–2 次），**用 `github-trending` 直接起稿的只有 2 篇**——账号叫"每天一个GitHub热榜项目"，实际很少直接从热榜取数
- 中位数 **4 条** `needsVerification`，**25 / 34 篇**正文含"未能核实 / 以官方为准 / 可能"这类对冲表述

以上数字可用本轮新增的校验器复核：`lwb/packs/spoken-video/spoken-video-number-consistency.mjs`（`checkNumberConsistency`）——把稿件正文里所有 ≥1000 的数字与该稿引用信号里的数字做集合比对，找不到即判为「素材里对不上」。全部 34 篇跑下来命中 3 篇，逐条看过：

| 稿件 | 命中数字 | 是不是问题 |
|---|---|---|
| 《别再干「黄金回收」副业了》 | 1000 | 否——正文自己的算术示例（金价跌 100 元，账面少 1000 元），不是引用的事实 |
| 《风光装机破 20 亿千瓦》 | 2000000000 | 否——正文引「公开数据说」，而该稿 `signals` 为空，属于素材缺失而非编造 |
| 《同时开几个 AI 写代码》 | 28000、41000 | **是**——正文说「Vibe Kanban 2.8 万多星」「Codewhale 4.1 万星」，而引用的信号里没有这两个仓库 |

也就是说：**34 篇里真实的数据类问题 1 例，且是「引了素材里没有的仓库」而不是「凭空编数」**——这恰恰证明问题不是编数字，而是根本没有数字可用。

校验器自身的判据（复盘后收紧过，理由见 `spoken-video-number-consistency.mjs` 里的注释）：

- 只看 ≥1000 的整数：小数字是稿子自己的结构计数（"三个方法"），不是引用的事实
- 年份按「2026年」的上下文识别，不按数值区间（2088 也是合法星数）
- 日期、IP、版本号里的数字段排除在外
- 英文 `k`/`M` 不当量级（`10 min`、`5 km`、`1,200 members` 会被误判）
- 中文数字（「六万五」）读得出来，但**不参与编造判定**——口播里的「六万」是取整说法，拿它跟素材的精确值比是误伤
- 提示措辞用「素材里对不上，请核对来源」，不用「编造」——素材快照可能本来就不完整

### 缺陷 2：钩子普遍超长，3 秒窗口装不下

按 `checkLength` 的 4.1 字/秒语速换算（实测脚本 `checkStructure` + 4.1 字/秒）：

| 指标 | 全部 34 篇 | 该账号 10 篇 | 爆款基线 |
|---|---|---|---|
| 首句朗读时长中位数 | 4.88 秒 | **6.10 秒** | 前 3 秒是留存闸门 |
| 首句 ≤ 3 秒的稿件 | 4 / 34 | **0 / 10** | — |
| 首句字数中位数 | 21 | 26 | ≤ 12 字 |
| 最长首句 | 8.5 秒 | 8.5 秒 | — |

参考口径（`video-hook-writer/SKILL.md`）："Spoken hook line under 12 words. Longer lines outrun the 3-second window at speaking pace."

典型对照：
- 「你刚下了一个新出的效率小工具，一打开就卡。关了还赖在后台吃内存，你肯定遇过。」→ 4.9 秒
- 「同一个 AI，同事用着比你顺手，差的不是模型，是他给 AI 装了『技能包』。」→ 4.6 秒

而蝉妈妈的知识科普型模板是 `【0-3s】颠覆认知：你以为...其实...`，海螺社的黄金三秒模板要求"第一句直接进正题"。当前提示词的钩子规则只说"钩子就是第一句话本身"，**没有任何长度上限**。该账号 10 篇**没有一篇**首句能进 3 秒——这不是个别稿子的问题，是提示词缺上限的必然结果。

### 缺陷 3：结构是一段平铺的说明，不是"拍"

当前唯一结构规则（`spoken-video-script.mjs:607`）：

```
结构：强钩子开场 → 快速承诺讲清什么 → 分层讲机制 → 生动但原创的例子 → 有风险意识的收尾。
```

实测段落数分布（34 篇）：中位 **50 段**，最长 **167 段**。而视频时长中位 377 秒（6.3 分钟）。这是"把一篇文章切成很多小段"，不是"5 个拍"。

对照 `youtube-script-writer/SKILL.md` 的节拍架构：3–5 拍，每拍 = mini-hook + 交付 + 桥；每 90–120 秒一个 pattern interrupt。

对照有米有数《抖音神眸3C品类打法拆解》TOP15 爆款的**统一脚本结构**（抽样 200 条深度分析）：

```
0-3秒   反常识否定 / 悬念
3-15秒  旧品类罪状清点
15-30秒 新品解法（演示优先）
30-60秒 信任与场景
收口    行动指令
```

实测该账号 10 篇对这个四段式的覆盖（用词面判据）：

| | 旧问题 | 新解法 | 信任锚 | 行动收口 |
|---|---|---|---|---|
| 命中 | 8/10 | 6/10 | 9/10 | 6/10 |
| **缺口** | — | **4/10 缺** | — | **4/10 缺** |

最典型的缺口是 Postman 那篇（讲完"证据"就收）和 Kimi K3.1 那篇（讲完"是什么"就收）——**没有"它具体怎么帮你干活"的演示段，也没有明确行动指令**。

### 缺陷 4：结尾没有具体互动指令，且常被"免责"稀释

| 指标 | 全部 34 篇 | GitHub 账号 10 篇 |
|---|---|---|
| 结尾 2 段内有明确互动指令（评论区/留言/说说/报个数） | **5 / 34** | 5 / 10 |
| 有任何互动词（含"聊"） | 8 / 34 | 7 / 10 |

海螺社的口播稿结构里，"行动"是三段骨架之一，且明确要求"**只留一个行动指令**，且和内容强绑定……别在结尾同时喊点赞收藏关注转发"。youtube-script-writer 要求"exactly one topic-specific CTA"。

实际稿件里的结尾长这样（Multica）：

> 最后提醒一句。这类工具更新快，界面和用法，隔一阵就可能变。我讲的这些，以你打开它那天为准。AI 帮你省的，是传达和盯梢。拍板的那一下，永远得是你自己。

这是一个**免责 + 金句**，不是互动指令。另有 8 篇的结尾句是"以官方文档为准 / 我没能核实"这类免责——`needsVerification` 越多的稿，结尾越容易被"我没核实"吃掉。

### 缺陷 5：提示词里有与账号不匹配的硬编码读者画像

`spoken-video-script.mjs:600`：

```js
`说人话（硬性）：把读者想成**一个不懂技术、想搞副业的普通上班族**。……`
```

"想搞副业"是**「发哥聊副业」账号**的读者画像，被硬编码进了所有账号的写稿提示词。这个账号的读者是"想学编程、想用开源工具提效但不想啃英文文档的职场人"。画像错配会让模型对着一群程序员讲"当个普通上班族"，把该讲的术语当成黑话全删掉。

**同时，黑话表本身也不覆盖这个账号的词**：`JARGON_TERMS` 共 40 条，提示词只注入前 24 条（`JARGON_TERMS.slice(0, 24)`）。未注入的 16 条里有 `打法`、`势能`、`转化漏斗`、`私域`——全是营销词。而该账号真正会出现的黑话一个没收：

| 词 | 在该账号稿件中出现次数 | 是否在黑话表 |
|---|---|---|
| 仓库 | 13 | 否 |
| 开源 | 9 | 否 |
| 权重 | 8 | 否 |
| 命令行 | 4 | 否 |
| 依赖 | 4 | 否 |
| 许可证 | 3 | 否 |
| 遥测 | 2 | 否 |

实测「同时开几个 AI 写代码」那篇正文里写了"遥测默认开着"，`jargonHitCount` 却是 **0** —— 质检放行了它。

## 二、外部爆款结构：可引用的证据

以下 5 份材料是本轮实抓的公开内容，作为改造依据。每条结论标注了性质。

### 2.1 蝉妈妈《抖音爆款视频的脚本模板》（公开可查）

- **性质**：平台方法论文档（含蝉妈妈自有数据口径），非我们账号的一手效果数据
- **知识科普型模板**（与我们账号赛道最贴）：
  ```
  【0-3s】  颠覆认知：你以为...其实...
  【3-15s】 原理讲解：用比喻/图示解释
  【15-25s】应用场景：生活中这样用
  【结尾】   价值强调：记住这几点
  ```
- **规律 3 低认知门槛**："文案简短：15 字内说清核心"、"信息聚焦：单视频只讲一件事"；蝉妈妈数据称"文案＜20字的视频平均播放量高32%"
- **规律 4 强互动设计**：提问式引导（"你遇到过吗？"）、争议性话题、挑战/接力
- **规律 6 节奏控制**：0-3s 吸引注意 → 3-15s 核心展示 → 15s 后深化 → 结尾互动引导
- **数据层**：爆款完播率普遍 >40%，3 秒完播率 >60%，点赞率 >5%，评论率 >1%

### 2.2 海螺社《口播稿怎么写？钩子+价值+行动》（公开可查）

- **性质**：内容服务商方法论，无实测数据背书
- **三段骨架**：钩子（前 3 秒，1 句）→ 价值（中间，主体 70%，每 5 秒一个信息点，"一条口播只回答观众的一个问题"）→ 行动（结尾，1 句）
- **黄金三秒 4 种钩子写法**：提问式 / 痛点式 / 反差式 / 利益预告式
- **数字人口播稿模板**（同一站）："第一句必须是完整的一句短话，**不超过 15 个字**，不能带从句"
- **禁忌**："别把结论一次说满，留个缺口比全盘托出更想让人往下看"；"结尾别拖尾巴，直接给结论或下一个动作"；"完播率低的时候…正确做法是逐句问'这句删掉，观众理解会不会受影响'"

### 2.3 海螺社《黄金三秒钩子：6 种开头模板》（公开可查）

| 模板 | 公式 | 适合 |

| 痛点直击 | 你是不是也 + 具体麻烦？ | 干货、教程、避坑 |

底线："开头承诺的，正片里一定要给"；"别每条都用同一个钩子，观众会腻"。

### 2.4 有米有数《抖音神眸3C品类打法拆解》（公开可查，样本 2630 条 / 深度分析 200 条）

- **性质**：跨品类（3C 硬件）样本，**不是科技知识账号**——借鉴的是"反常识否定 → 旧法罪状 → 新法演示 → 信任 → 行动"这个骨架，不是具体话术
- **TOP15 爆款统一脚本结构**（见上）
- **5 种已验证黄金三秒句式**（附素材编号与频次）：反常识否定式（"现在谁还买监控呀，太落后了吧"，十余条共用）、禁止式、**反差利益式**（9 秒短钩）、价格损失式、故事惊魂式
- **高频口播套路**：「砸机清单」（"一要…就砸；二要…就砸；三没…就砸"，≥8 条 TOP 素材）、「代际淘汰」（"第一代…第二代…第三代…直到第五代"）、动作演示（"轻轻吸上，安装就完成了"）、参数三连、圈人三连（"家里有老人小孩、养宠的、租房独居的，真建议备一台"）、**反向测评**（"它有两大缺点，没人跟你们讲"）
- **启示**：「代际淘汰」和「反向测评」直接对应我们账号的"新工具清一色 Rust"和"坑"两栏

### 2.5 `video-hook-writer` / `youtube-script-writer` SKILL（公开 skill 文档）

- **六公式**：Callout / Curiosity Gap / Transformation Promise / Controversy Opener / List Tease / Visual-First
- **硬限制**：口播钩子 <12 词；"makes a specific claim, not a vague one"；无问候、无背景铺垫、绝不"In this video I will show you"；"Do not deliver one hook; the winning variant is found by testing, not guessing"
- **平台校准**："**Shorts rewards the Curiosity Gap most reliably because the audience skews information-seeking**"（知识类受众的定向结论）
- **长视频节拍**：hook/body/payoff；3–5 拍，每拍 mini-hook + delivery + bridge；中点放 re-engagement trigger；每 90–120 秒一个 pattern interrupt（@150wpm ≈ 225–300 词）；payoff = 回顾 + **钩子里没说的额外洞见** + 恰好一个选题相关 CTA；"Do not bury the main point past the two-minute mark"
- **Do NOT**："Do not pad with filler transitions"；"Do not stack CTAs"

## 三、优化方案

改造点集中在两个文件：`lwb/packs/spoken-video/spoken-video-script.mjs`（写稿规则）与 `lwb/packs/spoken-video/spoken-video-signal-adapters.mjs` + `spoken-video-content-store.mjs`（事实供给）。

### 3.1 先修事实供给（P0，不修这条后面全是空谈）

**改动 3.1.1 — GitHub Trending 解析器补全星数**

`spoken-video-signal-adapters.mjs` 的 `parseGithubTrending` 现在只取 `stars today`。改为同时取总 star 与 forks，并把三者写进 `summary`，让它们随 `text` 一起进写稿层。

页面结构（本轮实抓确认）：

```html
<a href="/cloudflare/security-audit-skill/stargazers" ...>
  <svg ...octicon-star ...><path d="M8 .25a.75.75 ..."/></svg>
  65,243</a>
<a href="/cloudflare/security-audit-skill/forks" ...>
  <svg ...octicon-repo-forked ...></svg>
  4,236</a>
...
Built by 2,088 stars today
```

⚠️ **解析陷阱（本轮踩过）**：不能直接用"锚点之后第一个数字串"取星数——`<svg>` 里的 `<path d="M8 .25a.75.75 ...">` 含大量数字，会被误取（实测取到 `fork=3`、`总star=3` 这种值）。

**正确规则**（在 15 个仓库上实测 15/15 通过）：

```
取某个锚点（/stargazers 或 /forks）后面的数字：
  1. 定位锚点位置 i
  2. 从 i 起找第一个 </svg> 的位置 j
  3. 从 j 到下一个 </a> 之间，剥掉所有标签、压掉空白
  4. 该文本的第一个数字串就是该指标
```

注意 `/forks` 必须独立定位——不能假设它紧跟 `/stargazers`，虽然当前页面上确实是。

新的 `summary` 形如：

```
An extremely fast Python linter and code formatter, written in Rust. · Rust · 65,243 star · 4,236 fork · 今日 +2,088
```

三个数各有各的用处，**不能混着说**：总 star = 体量，今日新增 = 增长趋势，fork = 使用广度。账号定位要求"star 数与增长趋势必须有数据支撑"，那就必须同时给这两个，并且不能把"今日 +2,088"说成"总共 2,088"。

`normalizeNumber`（同文件:254）已能处理 `65,243`（去逗号）与 `2,088`，无需改动；但它**不处理 `+` 前缀**，所以今日新增要写成 `今日 +2,088` 这种带标签的形式，或在拼接时去掉 `+`。

**改动 3.1.2 — 信号传给写稿层时带上数值字段**

`spoken-video-content-store.mjs:974` 现在的 `text` 拼接丢掉了 `hotValue`。改为在 `text` 末尾补一行结构化元信息：

```js
payload: {
  source: signal.sourceId,
  text: `${signal.title}\n${signal.summary}${signal.url ? `\n${signal.url}` : ''}`,
}
```
→
```js
payload: {
  source: signal.sourceId,
  text: signalPayloadText(signal),
}
```

新增辅助函数（放在同文件），把 rank / hotValue 显式写出来，并在没有数值时明说"该来源未提供热度数值"：

```js
function signalPayloadText(signal) {
  const head = `${signal.title}\n${signal.summary}${signal.url ? `\n${signal.url}` : ''}`
  const meta = []
  if (Number.isFinite(signal.hotValue)) meta.push(`热度数值：${signal.hotValue}`)
  if (Number.isFinite(signal.rank)) meta.push(`榜单位次：第 ${signal.rank} 名`)
  return meta.length ? `${head}\n${meta.join('｜')}` : `${head}\n（该来源未提供热度数值，禁止编造数字）`
}
```

**改动 3.1.3 — 写稿规则：数字只能用素材里出现的**

现有规则已经写了"数字只能用信号素材里确实存在的"，但信号里没有数字，所以模型编。改动 3.1.1/3.1.2 之后这条才真正可执行。同时把**总 star 数**和**今日新增**分开表述——这是账号定位里"star 数与增长趋势"两个不同指标，混着说就是编趋势。

#### 3.2.3 钩子加硬约束：≤3 秒、≤15 字、自带具体事实（P0）

**新增规则**（插在现有钩子规则后）：

```
钩子长度（硬性）：第一句朗读时长不超过 3 秒——按 4 字/秒算就是**不超过 12 个字**（念出来一口气能念完）。超过就是没写完，不是"稍微长了点"。
钩子必须自带具体事实：钩子句里至少出现一个下面这四类东西之一——一个具体数字、一个具体场景、一个具体身份、或者一个具体反常识判断。没有具体内容的钩子（比如"这个工具很有意思"）等于什么都没说。
钩子和标题的关系：标题负责"这条讲什么"，钩子负责"为什么现在要听"。两者不能是同一句话换个说法——钩子里必须有一个标题上没有的信息。
钩子必须在正文第一句兑现：正文第一句必须和 hook 字段逐字一致（34 篇存量稿里 4 篇不一致，其中该账号 1 篇，剪辑时两处字幕对不上）。
```

最后一条是**可机器校验的**：`checkStructure` 现在只检查 `openingLength >= 12`，方向反了（它在鼓励钩子长）。改为同时检查首段长度上限。

> **实施后修正（本轮复盘）**：阈值最终定在 **12 字**，度量对象从「首段」改成「**首句**」，原来打算定的 40 字废掉了。两个理由都是实测出来的：
>
> 1. **40 字在真实语料上等于不触发**。34 篇存量稿的**首句**中位 21 字、最长 38 字——没有一篇超过 40 字，所以 40 字阈值实测只触发 3/34（那 3 篇是首段过长，不是钩子过长）。而按规则的字面口径（首句 ≤12 字），违反的是 **31/34**。取 40 等于把「可机器校验」这条规格架空了。
> 2. **旧的「首段不足 12 字 → 缺少钩子」下限与新上限直接打架**。上限压到 12 字后，一个 10 字段落、完全合规的钩子会被判「过短」。这个下限已删除——钩子够不够由「必须自带具体事实」那条规则管，不由长度下限管。
>
> 改完的实测：34 篇里 **29 篇触发「钩子太长」**，长度中位 21 字——这正是要抓的量级。

#### 3.2.4 结构规则改为"四段式 + 拍"（P0）

**现状**（第 607 行）：
```
结构：强钩子开场 → 快速承诺讲清什么 → 分层讲机制 → 生动但原创的例子 → 有风险意识的收尾。
```

**改为**（依据 2.1 蝉妈妈知识科普型 + 2.4 有米有数 TOP15 统一结构 + 账号定位五要素）：

```
结构（四段式，缺一段就是没讲完）：
1) 钩子：第一句就是钩子，≤12 字，带具体事实。
2) 旧问题：这东西是来解决什么麻烦的——先让观众认出自己的处境（"你是不是也……"）。这一段要让观众确认"这说的就是我"。
3) 新解法：它具体怎么干活——用动作讲，不用形容词讲。这一段必须有一个能想象出来的场景或动作（像"轻轻吸上，安装就完成了"），不要停在"它很好用"。
4) 收口：适合谁 + 有什么坑 + 一个具体互动问题。三件事都要有，"坑"不能省——这是账号定位里"客观评测+避坑提示"的落点。
```

同时把"分层讲机制""有风险意识的收尾"这类抽象说法换成可判定的动作。

#### 3.2.5 加"拍"与"进度暗示"（P1）

**新增规则**：

```
拍（beat）：一条视频按 3–5 拍来写，每拍 = 一个 mini-hook（这一拍要解决什么）+ 交付（这一拍讲什么）+ 桥（下一拍为什么值得听）。每拍开头一句话要能单独成立。超过 5 拍就会散，超过 3 拍会赶。
进度暗示：中段必须给一次"还有下文"的信号——一句"最重要的一点在最后"、或者"第三点最容易被忽略"、或者一次明确的转折（"但真正的问题在这儿"）。观众知道后面还有东西，才会继续看。
数字插入：中段（讲完前两拍之后、进入收口之前）必须有一个"数字重音"——一个具体数字 + 一句它的含义。这是知识类内容留人的锚点。
```

第一条解决实测的"段落中位 50 段"问题——写成"拍"而不是"段"。

第二条对应 `youtube-script-writer` 的 midpoint re-engagement trigger 与海螺社的"进度暗示"，两者都明确说这是拉中段留存最省力的做法。

#### 3.2.6 收尾：一个具体 CTA + 一句钩子里没有的洞见（P0）

**新增规则**（替换现有的收尾相关表述）：

```
收尾（三件事，一件都不能少，顺序固定）：
a) 适合谁 + 谁先别碰（这个账号的定位要求，也是观众最想要的决策依据）。
b) 一个具体的互动问题，指向本条内容本身，能一句话回答——不要"你怎么看"这种空问题，也不要在结尾同时喊关注点赞收藏转发，只留一个动作。
c) 一句钩子里没出现过的额外洞见（反常识的边界、或"它不能做什么"）。这句是把看完的人变成关注的人的那一句。
禁止：把"未能核实""以官方文档为准"当结尾。事实存疑的内容写进 needsVerification，不要占用最后一句——观众最后听到的应该是观点，不是免责声明。
```

**禁止那句是针对实测数据的**：25/34 篇正文含对冲表述，8 篇的结尾句就是免责。免责声明留在 `needsVerification` 字段里给作者看，不该被念出来。

#### 3.2.7 事实纪律加一条"不许拿 star 当唯一论据"（P1）

```
star 数只是"有人关注"的证据，不是"值得用"的证据。写了 star 数就要回答"涨得快为什么涨"（今日新增说明在涨，来源要能说清），否则只报数字不解释，等于搬运榜单。
```

这条直接对应账号定位里"区别于纯搬运榜单的账号，主打一个项目讲透"。

### 4.3 `benchmark` 包（「对标拆解」）的评估与最小改造

`lwb/packs/benchmark` 目前未在 `lwb/local/packs.json` 启用（现状：`analytics`、`spoken-video`、`publisher`、`manual-script-video` 启用）。它能做的是：粘贴对标爆款文案 → AI 拆解 → 沉淀方法论库 → 生成选题建议。

**现有拆解维度**（`benchmark-agent.mjs` 的 `TEARDOWN_SCHEMA`）：`summary` / `hookType` / `hookQuote` / `structure[]` / `pacing` / `titleFormulas[]` / `commentInsight` / `reusable[]` / `viralityScore`。

**能直接反哺写稿提示词的字段**：`hookType`（钩子类型）、`structure[].purpose`（段落作用）、`pacing`（节奏）、`titleFormulas`（标题公式）、`reusable`（可执行清单）。

**缺的四个维度**（对照本轮 2.1–2.5 的证据）：

| 缺失维度 | 为什么需要 | 建议字段 |
|---|---|---|
| 钩子**秒数**与字数 | 2.2/2.5 都把它列为硬限制，但 `hookType` 是定性标签，量不出长度 | `hookSeconds`（number）、`hookChars`（number） |
| **拍**（beat）划分 | `structure[]` 是段落级，拍是叙事单元，粒度不同 | `beats[]: {name, miniHook, promise, bridge}` |
| **CTA 条数与类型** | 2.5 要求"exactly one topic-specific CTA"，现在拆不出来 | `ctaCount`（number）、`ctaType`（string） |
| **信息点密度**（每 N 秒一个） | 2.2 要求"每 5 秒一个信息点"，这是可量化的节奏指标 | `infoPointsPerMinute`（number） |

**最小改造**：`TEARDOWN_SCHEMA` 加这 4 个字段 → `normalizeTeardownAnalysis`（`benchmark-store.mjs:114`）同步校验 → `buildTeardownPrompt` 的要求列表补对应约束 → `buildSuggestionsPrompt` 把 `beats[]` 和 `ctaType` 拼进给选题建议的上下文。

**但这是个产品决策，不是技术决策**：启用 `benchmark` 包意味着多一个能力包、多一份工作区数据、UI 多一个入口。**建议先只做 3.2 的写稿规则改造**（不依赖 benchmark），把 benchmark 的改造留到用户决定启用该包之后。当前 `benchmark` 的方法论库是空的（该包从未启用过），启用后需要先喂一批对标文案才有价值——而喂什么、喂多少，是运营决策不是代码决策。

## 五、这个方案解决不了什么

诚实标注边界：

1. **效果未验证**。本账号 10 篇稿件零平台指标，方案里的结构判据能证明"稿子按新规则写了"，不能证明"完播率会涨"。真正的验证要等改造后的稿件投放。
2. **样本外推有限**。有米有数那份是 3C 硬件品类（神眸摄像头），蝉妈妈是跨品类方法论；"反常识否定 → 旧法罪状 → 新法演示 → 信任 → 行动"这个骨架可以借鉴，具体话术不能照搬——硬件的"砸机清单"（"一要…就砸"）在开源项目解说里会变成人身攻击。
3. **视频形态与短视频方法论有落差**。已投递的 41 条视频**全部是横屏**（`landscape/wechat` 6 条、`landscape/douyin` 35 条，竖屏 0 条），时长中位 216 秒、最长 516 秒。这是知识类横屏长视频，不是抖音竖屏短视频。蝉妈妈/海螺社那套"0-3 秒 / 3-15 秒 / 最后 3 秒"的分段是按 15–60 秒竖屏设计的，套到 6 分钟横屏上需要按拍重新折算——本方案给的「拍」与「进度暗示」就是为这个落差做的折算，但**折算比例没有实测依据**。
4. **`analytics` 没有绑定该账号**，投放后要手动补绑定才能拿到指标。
5. **选题层没动**。实测 20/34 篇标题以"别再"开头、12 篇是副业避坑类——「发哥聊副业」的选题习惯没有泄漏到 GitHub 账号（后者标题形态正常），所以选题层本次不改。但 GitHub 账号的选题**也**有 `github-trending` 信号只被用了 2/10 次的问题，这属于选题层与信号圈选的调整，不在本次写稿规则范围内。

### 6.2 独立审查查出并已修掉的问题

审查员（独立会话，只读不改）在实测中查出 5 个阻断、7 个应当修的问题，其中**实现偏离规格**与**规格本身有缺陷**各有：

**实现偏离规格（已修）**
1. `githubCounterAfter` 的 href 正则无路径边界——仓库名本身叫 `forks` 时，标题链接 `href="/owner/forks"` 会命中 `/forks`，总 star 被当成 fork 数。改为 href 必须**精确等于** `/<owner>/<repo>/<counter>`。
2. `</svg>` 搜索无上界——目标锚点里没有 svg 时会跨到下一个锚点取数。改为先按 `</a>` 切出锚点元素边界，只在元素内部找。
3. `candidate()` 里 `Number(null)` 是 0 且 0 是有限数——缺「今日新增」时 `hotValue` 被钳成 0，写稿层收到「热度数值：0」，那是一个凭空造出来的零。改为 `null` 保持 `null`。
4. `signalPayloadText` 的「禁止编造数字」兜底挂在 `hotValue` 与 `rank` 的**合取**上——而 `rank` 从不缺失（RSS 给的是条目序号），所以这条兜底在 2315 条真实信号里**一次都没触发**。改为只看 `hotValue`。
5. `compact()` 的 `summary.slice(0, 300)` 从尾部截断，把追加在末尾的三个计数器切掉（本机 50 条 github-trending 信号里 5 条丢计数）。改为拆分描述与计数器。
6. 热度数值与榜单位次漏进**选题**提示词——选题阶段被具体星数锚定。改为选题提示词只渲染标题与描述。

**规格本身有缺陷（已改规格并同步实现）**
7. 钩子上限 40 字 vs 规则 12 字，且量的是「首段」不是「首句」——实测 40 字阈值在 34 篇存量稿上只触发 3 篇，而按规则口径（首句 ≤12 字）违反的是 31 篇。改为按首句量、阈值 12 字。
8. 旧的「首段不足 12 字 → 缺少钩子」下限与新的 12 字上限直接打架（10 字段落的合规钩子会被判过短）。下限已删。
9. `SCRIPT_DRAFT_SCHEMA.hook` 的字段描述还写着「15-30 字」，与 ≤12 字规则直接矛盾（写稿模型看的就是这个描述）。已改。

### 6.3 复盘后收紧的校验器判据

校验器接进生产链路后，误报会直接出现在用户的质检建议里，所以判据逐条收紧了：

- 英文 `k` / `M` 不当量级（`10 min`、`5 km`、`24 kWh`、`1,200 members` 曾被当成千/兆）
- `万亿` 当成一个量级（曾被当成「万」，2.8 万亿算成 28000）
- 日期、IP、版本号里的数字段排除
- 句末的「12000.」要算进 12000
- 中文数字（「六万五」）读得出来，用于跨写法匹配，但**不参与编造判定**——口播里的「六万」是取整说法
- 提示措辞用「素材里对不上，请核对来源」，不用「编造」
