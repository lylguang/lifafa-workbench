## 0. 结论先行

用户描述的逻辑**成立且自洽**（经两次修正后），可以整理为：

```
账号定位（可选 · 全局约束）
选题四输入：标题 / 切入角度 / 信号源 / 具体信号（四选一必填，填了就参与）
        ↓ 分层组装（不是排他路由）
素材层（可叠加）：具体信号 ∪ 来源信号 ｜ 无素材时：按标题检索 → 全池兜底
约束层（全注入）：标题主题 · 角度意图 · 定位边界
        ↓
DSH 统一执行（不变）：会话/工具生成候选，联网搜集走审批
        ↓
恰好 5 个候选，默认选中第 1 个 → 人工确认 → 锁定选题、依据写入产物（状态机不变）
```

它与 my-agent 的主线逻辑同构，差异点只有三处（候选数量 5 vs 3、选择权归人、联网搜集经 DSH 工具而非模型直连搜索服务），都在合理范围内。

## 1. 参考实现 my-agent 的选题逻辑（核查结果）

### 1.1 profile（账号定位）

`config/agent.profile.example.json` 中与选题直接相关的字段：

- `positioning` / `audience`：定位与受众描述；
- `mainline_pillars` / `adjacent_pillars` / `exploration_pillars` + `direction_mix`：内容方向与配比；
- `domain_policy`：内容边界、核心词/上下文词、禁用角度词、语义主题簇与冷却策略；
- `persona` / `production_style`：人格与制作风格（主要影响写稿，不影响选题）。

选题时被压缩进 prompt 的是 `compactTopicAccountContext()`（agent_ops_cli.js:5600）：name、platform、positioning、audience、三类 pillars、target_mix、preferred_lane、recent_topics（近 12 条已选题）。**所有字段都允许为空**——没有 profile 时选题管线照样跑，只是少了方向约束。这正是"没有 profile 也能提供选题"的参考依据。

### 1.2 主线选题：统一信号两阶段（unified_signal_two_pass）

`generateTopicOnce()`（agent_ops_cli.js:5919）：

1. **收集信号池**：公开热榜（baidu/toutiao/zhihu 等）+ AI 日报信号，合并去重；
2. **第一遍 · 信号筛选**：`unifiedSignalSelectionPrompt` 让 LLM 按账号定位把信号池筛到 ≤24 条；模型失败则兜底用全部信号；
3. **第二遍 · 候选生成**：`unifiedTopicCandidatePrompt` 基于筛选后信号生成**恰好 3 个**候选，每个候选携带 `title / hook / audience_problem / audience_payoff / content_core / why_now / video_form / source_signal_ids`（可追溯到具体信号）；
4. **本地标注与选择**：方向匹配、语义查重、标题精确重复门禁、事件复用冷却；全部被拦时有一次"换新信号重生成"的恢复尝试，最后兜底选复用最少的候选；
5. 产物落盘为 `topic_batch`，含完整 `source` 审计。

### 1.3 用户指定选题（user_directed）

`createUserDirectedTopic()`（agent_ops_cli.js:6267）：**只要求 title**，直接建一个 `topic_batch` 产物进入生产；资料搜集交给写稿阶段的联网检索。这是 my-agent 里最接近"只给一个标题"的形态，但它的候选生成被推迟到写稿阶段，而用户希望的是**在选题阶段就给出 5 个候选**——这一点 my-agent 没有现成实现，需要 LWB 自己组装。

### 1.4 「5 选 1」的参考先例

公众号热点实验（`listWechatHotspotExperimentTopics`，agent_ops_cli.js:8020）：给出 top 5 个选题、**仅供人工选择、不自动选题**（"请从前五个选题中选择一个"）。用户要的"5 个候选 + 人选一个"在 my-agent 里有此先例，只是主线统一选题是 3 个。

## 2. LWB 选题模块现状（差距）

`client.js:482` TopicsPage 当前形态：

- 输入：**标题（必填）+ 切入角度（可选）+ 勾选活跃信号（至少 1 条必填）**——两个必填，比用户设想更严格；
- 提交：`create` 建项目 → 逐条 `commit(stage:'signals')` 写信号依据 → `commit(stage:'topic')` 锁定；
- 信号列表是 active 信号平铺，无来源过滤、无信号源维度选择；
- **没有**任何 AI 生成、没有账号定位、没有候选列表（用户直接手写标题）。

差距总结：现状 = 用户设想中最简单组合的手工弱化版（且强制标题+信号双必填）。要升级成完整形态，缺：①账号定位存储与注入；②信号源维度的选择器；③输入分层组装与校验（四选一必填、填入即参与）；④候选生成能力（经 DSH）；⑤候选列表 + 默认选中 + 人工确认的交互。

## 3. 目标形态梳理

### 3.1 账号定位模块（多账号，可选，位于信号之前）

- **形态**：账号定位库每条记录包含 `id / name / status / revision / positioning / audience / pillars / boundary`。只保留选题和写稿相关字段；制作发布配置仍属于包或项目层。
- **位置**：独立菜单「账号定位」位于信号之前，数据落 `.lwb/spoken-video/topic-profile.json` schema 2；旧 schema 1 单 profile 自动迁移为一条「原有账号定位」。
- **选择与快照**：选题页可选择一个 active 账号或明确不使用账号定位。生成记录和确认后的 `topic` artifact 都保存选中账号的快照；账号之后被编辑、切换或归档都不会改变已有项目。写稿直接使用 topic 快照；如在写稿页改绑账号，则重写 topic 阶段并失效下游。
- **非必须**：不选择账号时全链路可用——生成 prompt 注入空上下文；默认账号仅用于预选，不能替代选择或项目快照。

### 3.2 选题页四输入与校验

| 输入 | 性质 | 说明 |
|---|---|---|
| 选题标题 | 可选 | 用户自拟标题/主题句 |
| 切入角度 | 可选 | 编辑意图，约束生成方向 |
| 选择信号源 | 可选 | 来源粒度：百度热榜、今日头条、36氪等（复用现有来源库） |
| 具体信号 | 可选 | 条目粒度：信号池里勾选具体条目（含「送入选题」预选） |

**校验：四项至少填一项，全空拦截。凡填入者一律参与生成——四选一只是下限，不是排他选择。**

### 3.3 输入组装（三次修订：分层组装，不是排他路由）

初版"优先级链（具体信号 > 信号源 > 标题）"存在误读风险——像是选了一个就忽略其他。正确语义是**分层组装**：四项输入按性质归入两层，层内叠加、层间组合，任何录入都不会被丢弃。

**素材层（决定候选基于什么事实）——可叠加：**
- 选了具体信号 → 这些信号进入素材集；
- 选了信号源 → 该来源下的信号（必要时先触发一次采集）进入素材集；
- 两者同填 → **取并集**（例如"百度热榜"＋从今日头条手动勾选的两条），无需取舍；
- 只填标题/角度（无素材）→ 先按标题在信号池检索相关条目；检索仍空则落到全量信号池（今日/近期）。

**约束层（决定候选往哪个方向走）——全部注入：**
- 账号定位（有则注入）：方向、受众、领域边界；
- 选题标题（有则注入）：候选必须围绕该主题展开；
- 切入角度（有则注入）：候选按该编辑意图组织（如"全部走避坑角度"）。

典型组合示例（覆盖用户列举的场景）：

| 输入组合 | 素材 | 约束 | 对应 my-agent 形态 |
|---|---|---|---|
| 仅信号源（如百度热榜、今日头条、36氪） | 所选来源的信号 | 定位（如有） | 统一信号两阶段，来源限定版 |
| 标题（+角度可选、+信号源可选） | 标题检索命中的信号；无命中时全池 | 标题 + 角度 + 定位 | 介于 `user_directed` 与对话式生成之间 |
| 具体信号（+标题/角度可选） | 用户所选信号（跳过第一遍筛选） | 标题 + 角度 + 定位 | 统一信号两阶段（信号已预选） |
| 仅切入角度 | 全量信号池 | 角度 + 定位 | **`/topic once` 默认形态**加角度约束 |
| 四项全填 | 具体信号 ∪ 来源信号 | 标题 + 角度 + 定位 | 上述形态的叠加，组装逻辑天然支持 |

此前文中的"模式 A/B/C/D"降级为这四类典型组合的简称，**不再是排他分支**。组装结果只有一个去向：统一生成契约（3.4）。

边界确认：
- **只有 profile、四输入全空**：仍被"四选一必填"拦截——"凭定位随便给几个"留作未来的"每日选题推荐"，当前不开口子。
- **只有角度、连 profile 也没有**：可执行（全池 + 仅角度约束），结果偏散；页面提示"配置账号定位后选题会更准"，不硬拦。

### 3.4 统一输出契约

- **默认 5 个候选，信息不足可少于 5，不硬凑**（四次修订定案：prompt 要求"最多 5 个、且仅在信息足以支撑时产出"；生成 3~4 个属正常，页面如实呈现数量）；
- 每个候选字段参考 my-agent：`title / hook / content_core / why_now / video_form / source_signal_ids`（可追溯）；
- **默认勾选第 1 个**，人工可改选——选择权始终在人（对应 my-agent 公众号实验"仅供人工选择，不自动选题"的纪律；my-agent 主线的自动选择器在 LWB 不搬）；
- 确认后走现状链路：建项目 → 候选引用的信号写 `signals` 依据 → `topic` artifact（title + angle + 候选来源审计）。

### 3.5 生成能力的落地姿态（架构约束 · 三次修订确认）

**核心确认：无论用户如何录入、走哪类典型组合，选题生成都由 DSH 执行，这是不变项。** LWB 不维护第二套模型运行时（01-架构红线、12 文档），因此不存在"包内自己调模型"的路径；所谓"生成 5 个候选"这件事，唯一执行主体就是 DSH。此前把"信号池检索 vs DSH 搜集"写成二选一（B1/B2）是表述错误——**信号池检索只是 host 侧的数据准备（本地过滤、按来源/关键词圈定素材），不产生智能；智能环节（筛选、组装、生成候选）恒定经 DSH**。

按文档 14 决策 1 已拍板的路径 **(a)**，固定流程为：

1. 包在 host 侧按 3.3 组装输入（素材层 + 约束层 + 账号定位），这是纯本地规则动作；
2. 经 `ctx.tools.register(defineTool(...))` 注册的选题工具（如 `spokenVideo/generateTopics`）由 DSH 会话中的模型调用，或经 `ctx.agents` 会话执行；凭据、计费、审批走 DSH 原生边界；
3. 需要联网搜集时（用户没给够素材、或要求补充外部信息），由 **DSH 的联网工具**完成并经审批——这与"在对话模块直接让 DSH 提供选题"是同一条执行链，包内不私接搜索。

一句话：**用户在选题页填的一切，最终都是交给 DSH 去执行的；选题页只负责组装上下文与呈现结果。**

### 3.6 页面设计（四次修订 · 用户方案评估通过）

用户提出：**左侧录入与选择信号，确认后右侧动态显示 DSH 执行过程（类似对话中的执行过程），执行完毕折叠过程、显示候选（默认 5 个、信息不足可少于 5、默认选中第 1 个）。** 评估结论：方向正确，采纳；在一个技术约束下微调呈现粒度。

**技术约束（先讲清）**：能力包页面与主机之间只有 `connection.rpc.call`（请求/响应）与局部订阅；包**拿不到 DSH 会话的事件流**（12 文档红线：包不能 import dsh-bundle client）。因此"逐字流式模型输出"做不到，右侧执行过程走**主机侧进度记录 + 客户端轮询**——与"来源管理/采集记录"同款审计流姿态（文档 14 既定："进度与日志进采集记录同款审计流"）。呈现的是**结构化步骤**（组装 → 检索 → DSH 生成 → 核对），清晰、可审计，符合工作台定位。

**布局**：左右分栏。

- **左栏 · 录入区**（固定可见）：四输入自上而下——选题标题（文本）、切入角度（文本）、信号源（多选徽章，复用来源库）、具体信号（勾选列表，带来源与评分，接收「送入选题」预选）；底部一行只读显示已注入的账号定位摘要 + 「确认 · 交给 DSH 生成」按钮。四选一校验在此：全空禁用提交。
- **右栏 · 动态区**（三态）：
  1. **待确认态**：回显本次组装给 DSH 的输入摘要（素材层 N 条信号 + M 个来源 · 约束层标题/角度/定位），让用户确认"系统理解了我填的东西"再执行；
  2. **执行中态**：结构化步骤流，逐步点亮（组装输入 → 检索信号池（命中数）→ DSH 生成候选（经 DSH 工具、审批走 DSH 边界）→ 核对去重），带运行中徽章与已耗时；
  3. **完成态**：执行过程自动**折叠**为一行摘要（用时 + 步数，可展开复查）；下方候选列表——默认 5 个、不足则如实呈现、默认选中第 1 个、点击可改选；每张候选卡显示标题 + 切入角度/形态 + 依据信号数与来源；底部「重新生成」与「确认选题 · 建项目」两键。

**细节约定**：执行中左栏锁定（防止边跑边改输入造成歧义）；「重新生成」保留输入、允许追加修改；确认后右栏保留候选快照写入 `topic` artifact 审计（谁生成、依据哪些信号、人选了哪个）；无会话/无定位时的空态与降级提示沿用现有 `NeedSession` 模式。
