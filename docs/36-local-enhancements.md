## 二、配音：接入小米 MiMo 云端 TTS

**改动前**：配音走本地 ComfyUI 的 LongCat-AudioDiT-3.5B，需常驻约 23GB 内存；`keep_model_loaded: true` 导致模型一旦加载就不再释放。

**改动后**：接入小米 MiMo 云端 TTS，并保留本地作为可切换备选。

- **方式开关**：`ttsProvider` 配置项（`cloud` 默认 / `local`），配置页两个互斥选项，切换时未选中的参数区自动置灰。
- **接口适配**：小米的形态是 `chat/completions` 而非 OpenAI 的 `/v1/audio/speech`——待合成文本放 `assistant` 角色，风格指令放 `user`（不会被念出来），结果取 `choices[0].message.audio.data`。
- **声音复刻**：有参考音频时自动切 `mimo-v2.5-tts-voiceclone`，参考音以 data URL 内联，省掉上传步骤。
- **引擎解耦**：8188 引擎重命名为「字幕引擎」并在卡片上标注「服务于：仅字幕 / 字幕+本地配音」。**关键认知**：8188 同时服务配音和字幕，云端模式下它仍为字幕而运行，不能被整体禁用。

**收益**：配音不再占用本机内存与显存；云端合成把算力从本机移出，与生图/字幕不再争抢 16GB 显存。

## 三、音画同步：场景边界取自真实语音时间轴

这是本轮最实质的修复。

**根因**：视频创作 Agent 在沙箱内**拿不到语音时间轴**，只能按稿件段落长度估算秒数写场景表。语音节奏与文本比例差异很大（数字读法、停顿、语速都在变），误差累积后**画面比语音超前 2–3 个完整章节**。实测那支视频：18 个场景里有 13 个边界切在语音句子中间。

**为什么拿不到**：关掉「烧录字幕」时，`inputs/subtitles.srt` 被写成空文件——而它正是分节的唯一依据。

**三道防线**：

1. **无时间轴不制作**：字幕产物成为视频制作的硬性前置条件。即使用户不想烧字幕条，也必须先生成一次（它同时提供时间轴）。报错明确引导操作路径。
2. **时间轴始终交付**：`inputs/subtitles.srt` 无论是否烧字幕都写入真实内容；创作提示词要求场景边界必须从该文件的真实时间戳推导，且写完场景表要回查语义是否对应。
3. **渲染前自动核对**：新增 `inspectTimelineAlignment()`，统计有多少场景边界落在语音句子内部，超阈值即拒绝渲染并给出可执行修复指引。

**检测方法上的一个坑**（值得记录）：不能用「场景边界到最近语音段首的距离」判断同步——语音平均 5 秒一句，任何时刻距离最近句首都只有 1–2.5 秒，该指标恒小、测不出错位。正确判据是**边界是否切在句子中间**。

## 四、字幕与音效

### 字幕与语音对齐

**改动前**：字幕时间轴按每句字数占比估算（因为字幕文本换成了原稿、丢了 ASR 时间戳）。TTS 停顿不均匀，实测 84 条字幕里 20 条在开口前 0.46–0.94 秒上屏。

**改动后**：用 ffmpeg silencedetect 量出真实语音区间，把每条字幕的切换点吸附到最近的句间停顿、固定在开口前 0.12 秒出现；过短条目并入相邻条目（文案零丢失）。

顺带修掉一个隐藏缺陷：吸附逻辑曾因 ESM 模块里误用 `require` 而**静默降级**（被 catch 吞掉），导致修复长期未生效。现已改为显式日志 + 诊断标志。

### 动效音效

**改动前**：成片完全没有音效——任务工程根本不生成音效素材，且音轨只有旁白。

**改动后**：用 ffmpeg 本地合成三枚短音效（whoosh / pop / ding）放进任务工程，供创作 Agent 在关键动画节点铺设。

**关键点**：初版音效「合成成功但听不见」——旁白峰值 −4.6dB，而音效峰值只有 −16.7 ~ −25.5dB，**低 12–21dB，人耳靠瞬态峰值感知音效，等于完全淹没**。现用 `loudnorm` 归一化，实测混音中 whoosh 1.80×、pop 1.92×、ding 1.34× 高于邻域。

### 字幕条定位

字幕条原按中心定位，单行/双行切换时整块上下跳动。改为底部锚定（固定高度容器 + `align-items: flex-end`）。

## 五、审片能力：修复视觉盲区

**改动前**：独立审片 Agent 的 `read_image` 全部被拒——`deepseek-v4.1-flash` 未声明图像输入，pi-ai 默认只给 `['text']`。审片三轮全部无条件失败，任务必然不通过。

**根因**：**声明缺失，不是能力缺失**。网关实际支持图像（实测真实抽帧返回了准确描述，含中文文字），只是 DSH 未被授权去尝试。

**改动**：`settings.yaml` 模型条目增加 `input: [text, image]`。

**顺带解开一个自相矛盾的死结**：审片提示词把「是否退化成文字卡片」的判据隐含成「有没有实拍素材」，而创作提示词明确禁止使用外部素材——导演无论怎么画都过不了。现已在审片提示词中明确：程序化绘制是本片的既定画面语言，缺实拍不是缺陷。

## 六、稳定性修复

### Windows 原子写入 EPERM

**问题**：选题任务 11 次里失败 7 次，报 `EPERM: rename`。

**根因**：Windows 上 rename **目标文件**只要被任意句柄打开（哪怕只读）就拒绝。而工作台前端每 1.5 秒轮询状态、读那个 1.2MB 状态文件——写入的 rename 撞上读窗口就失败。这解释了为什么连点三次重试全失败：轮询是持续的。

**改动**：6 处原子写入加 `EPERM`/`EBUSY` 退避重试（总窗口约 8.6 秒）+ 失败时清理临时文件。实测 12 次并发写入全成功、延迟 6–13ms、无残留。

### 路径与暂存

- `dsh-launcher.mjs`：TEMP/TMP 重定向到 `E:\lifa-scratch\temp`（系统盘曾只剩 5.8GB，渲染会因 ENOSPC 失败）。
- `pack-workspaces.mjs`：路径比较改为大小写不敏感（Windows `realpath` 会把盘符大写化，导致合法路径被误判为符号链接重定向，表现为**能力包侧边栏整体空白**）。

## 七、媒体桥接控制台

原本是 7 个 `<h2>` 线性堆叠的单栏页面，主次不分：当前不用的参数与每天要填的 API Key 视觉权重相同；字幕 ASR 被错放进「配音配置」；状态散落三处。

重做为专业后台布局：

- **两栏 + 1200px 内容宽度约束**（首版漏了最大宽度，导致超宽屏上输入框横跨 2500px）。
- **标签左置表单**（104px 标签列），替代垂直堆叠。
- **按实际链路分组**：配音（云端）/ 字幕（本地）/ 音色库 / 高级（折叠）/ 使用提示。
- **任务队列改造**：状态过滤（全部/进行中/失败）、固定高度滚动、保留上限 500 → 100 条、新增「清空已结束」。
- **新增接口**：`GET /admin/logs`（日志尾部）、`POST /admin/tasks/clear`。
- **运行日志面板**：折叠区懒加载最近 60 行。

## 十、定时任务音色预设与渠道跟随（2026-09-30）

**改动前**：定时任务无法指定音色——想给某个账号固定音色，只能先在「配音 / 字幕」页人工跑一次确认效果，每轮实际用的都是系统默认音色。更隐蔽的问题是渠道：任务运行时配音请求被归一化**硬编码回百炼默认值**，即使「配音 / 字幕」连接已切到本地桥接，定时轮仍打云端百炼（2026-09-30 09:00 轮次即因百炼 key 失效而整轮失败，手动任务却正常）。

**改动后**：

- **任务级音色预设**：新建/编辑定时任务时可选择「系统默认音色（Tiffy）」或**上传参考音频**（MP3/WAV/M4A/OGG，≤20 MiB），支持语速（0.5–2）与音量（0–2）参数；预设对该任务的每一轮生效，表单校验、任务描述文案同步更新，选了上传但未传音频时禁止保存。
- **参考音频逐轮落盘**：新增 `stageScheduleVoiceReference`——上传的参考音频先存入共享 `voice-references/` 工作区并校验标识一致，每轮开始时复制进当轮项目 `audio-media/references/`（覆盖写，重试幂等），使 `startVoiceover` 能以项目相对路径取到参考音。
- **渠道跟随连接配置**：调度轮的配音与字幕请求显式传 `connection.provider`（`bailian`=云端 / `scitiger`=桥接端点），与手动任务同源；音色预设本身**不冻结 provider**，执行渠道始终跟随当前配音服务配置，切换云端/本地不需要改任务。
- **签名对齐与测试**：`stageScheduleVoiceReference` 改为与 media-host 其余公开方法一致的 `(agent, request)` 风格；新增调度轮回归测试（参考音频逐轮落盘、provider 不被预设冻结）与客户端契约测试（新建/编辑/上传/校验四种路径）。

## 十一、升级边界

`vendor/deepseek-harness` 保持锁定在 `dsh-v0.1.6-alpha.1` 且**无源码改动**，所有增强都在 `lwb/` 内，符合上游的升级约定。

如后续需要跟进 DSH 内核升级（上游已到 `dsh-v0.2.0-rc.2`，相差 3298 个提交），有两处已确认的阻塞点：

1. **`packages/settings/settings-file` 被删除**——替换为 `dsh-settings` + `dsh-config-editor`，且 `settings.yaml` 的热加载能力不再存在。本仓库 `lwb/dsh-bundle/index.mjs` 使用了它的 `installSection` API（注册的 `lwb-workbench` 段目前只是占位，实际业务影响有限，但需改写）。
2. **Session 日志格式 v3 → v4**——上游提供读取迁移，旧文件仍可加载，但内容结构有变化。

另有一处行为收紧需注意：Windows ACL 沙箱中，以前静默跳过的 Modify-only 目录授权现在会显式失败。
