> 历史设计/验收记录，包含当时的方案与限制，不作为当前使用指南。当前入口见[文档索引](README.md)和[快速开始](quickstart.md)。

> 状态：2026-09-05 分析完成，用户拍板按推荐方案实施（方案 A + 卡片 P0/P1 一次做完 + 直接落代码验收），当日落地完毕。依据：`lwb/packs/spoken-video/` 现状代码、[12 场景能力包](./12-capability-packs.md)、[17 选题模块分析](./17-topic-module-analysis.md)、[20 信号页视觉美化方案](./20-signal-page-visual-polish-plan.md)。
> 用户两个问题：① 账号记录 V1、V2 版本信息好像没有必要；② 账号卡片过于平淡，是否重新设计。

## 0. 现状盘点

### 0.1 数据模型

账号库（`accounts.json`，schema 2）每条记录：`id / name / status(active|archived) / revision / positioning / audience / pillars / boundary / updatedAt`。

`revision` 的写入点（`spoken-video-content-store.mjs`）：

| 写入点 | 行为 |
|---|---|
| `createAccount` | 初始 `revision: 1` |
| `updateAccount` | `revision + 1` |
| `setAccountStatus`（归档/恢复） | **也 `revision + 1`**（⚠ 见 1.2） |
| 旧版 `setProfile` 兼容写入 | `revision + 1` |

快照侧（`spoken-video-topic.mjs`）：`parseAccountSnapshot` 要求 `revision` 为 ≥1 的安全整数；选题确认时账号以**不可变快照**（含 revision）写入 `topic` artifact，项目从不持有活引用。

### 0.2 `revision` 的全部触点

**功能层（1 处）**：

- `client.js:1127` `sameAccount` 比较——写稿页判断「项目快照账号 === 当前所选账号 且 版本相同」，版本不同则允许「更换账号并重置下游产物」。这是 revision **唯一**的功能性作用：检测项目绑定后账号是否又改过。

**显示层（8 处，全部在 `client.js`）**：

| 位置 | 现文案 |
|---|---|
| 801 账号卡页脚 | `v{n} · 保存于 {时间}` |
| 819 编辑抽屉头 | `版本 v{n} · 启用/已归档` |
| 843 抽屉说明 | 「保存后生成新的定位版本…」 |
| 861 归档行 | `v{n} · 归档于 {时间} · 快照保留在已确认项目中` |
| 1013 选题页 | `本次将使用「{name}」v{n} 的定位约束` |
| 1188 写稿页 | `账号定位：{name} · 版本 {n}（项目快照）` |
| 1190 写稿页下拉 | `{name} · v{n}（默认）` |
| 1192 写稿页说明 | 「账号会以当前版本写入新的选题工件…」 |

**测试**：`spoken-video-content-store.test.mjs:223` 断言新建账号 `revision === 1`。

### 0.3 账号卡片现状结构

```text
┌ sv-acc-card（button，纯文本四层）────────────┐
│ [名称 14px/700]              [默认|启用|待完善] │ ← 一枚 pill 混装三种语义
│ 定位摘要 2 行（positioning || audience || 占位）  │
│ [方向 chip] [chip] [chip]                        │
│ ───────────────────────────────────────────── │
│ v{n} · 保存于 09/05 12:00    受众 · {audience}  │ ← 11px 页脚
└──────────────────────────────────────────────┘
```

## 1. 问题一：V1/V2 有没有必要

### 1.1 `revision` 到底是什么

它**不是**乐观锁（`updateAccount` 没有 expectedRevision 校验，盲加 1），也**不是**可回溯的版本——系统不保留任何历史版本内容，旧定位无处可查、不可回滚。它实际只是一个**单调递增的修改计数器**，「版本」这个词名不副实。

### 1.2 现存缺陷：归档/恢复也 bump revision

`setAccountStatus` 把归档和恢复都当作 `revision + 1`。后果：一个账号归档再恢复后，内容一字未改，写稿页的 `sameAccount` 比较却判定「版本不一致」→ 提示用户重新绑定、重置下游产物。这是**误报**，属于设计瑕疵，顺手应修（状态变更不是内容变更）。

### 1.3 结论与选项

用户直觉成立：**显示层的 V 编号对用户没有决策价值**。用户关心的是「这个项目用的是不是账号的最新定位」，这是一个布尔问题，不需要暴露计数器。功能性作用（快照同步检测）保留即可。

| 选项 | 内容 | 改动面 | 评价 |
|---|---|---|---|
| **A（推荐）** | `revision` 字段保留在数据层，仅作快照同步指纹；**8 处 UI 显示全部移除**；`setAccountStatus` 不再 bump；写稿页版本不一致时改提示「该账号定位在你绑定后已更新，可重新绑定」 | 小：`client.js` + `setAccountStatus` 1 行 + 文案 | 收益/风险比最优；快照校验、测试无需动 |
| B | 字段连根删除（零兼容），同步检测改用快照内已有的 `updatedAt` 比较 | 大：快照校验、生成记录、测试全动 | 更彻底但收益边际；`updatedAt` 同样够用，可作后续清理 |

无论选哪个，843/1192 等「生成新版本」文案都要改写为「保存后仅影响后续新选题」语义。

## 2. 问题二：账号卡片为什么平淡

### 2.1 具体问题

1. **零视觉锚点**：四层全是文字，没有头像/标识。账号是「人格/身份」实体，却和一条设置项长得一样。对比信号卡片已在 [20](./20-signal-page-visual-polish-plan.md) 中获得平台 glyph 徽标，账号卡反而成了包里最素的一块。
2. **徽章语义混装**：一枚 pill 同时承担「默认 / 启用 / 待完善」，默认账号若未完善会显示「默认」而掩盖待完善状态，信息丢失。
3. **页脚冗余且自相矛盾**：左半边是噪声（V 编号 + 绝对时间戳），右半边「受众」与摘要行重复（摘要本身会 fallback 到 audience），300 字上限的受众被压进 11px 单行，截断难看。
4. **「待完善」太弱**：只有橙色描边 + 橙字。账号已有「Agent协助完善」能力，卡片却给不出「还差什么、完善度多少」的行动指引。
5. **时间展示陈旧**：绝对时间戳 `09/05 12:00`，与信号页已改用的相对时间方向不一致。

### 2.2 重塑方向（沿用信号卡已建立的视觉语言）

```text
┌ 账号卡（目标形态）────────────────────────────┐
│ [名] 老傅聊 AI            [默认] [已完善]      │ ← 单字 glyph 头像（名称首字，名称派生确定性色相）
│ 面向普通创作者的 AI 工具解读…（定位摘要 2 行）    │   + 默认/状态两枚徽章分离
│ ▓▓▓▓▓░░ 完善度 3/4                             │ ← 定位 4 字段（定位/受众/方向/边界）分段进度
│ [工具拆解] [行业观察] [效率方法]                 │ ← 方向 chips 保留
│ ───────────────────────────────────────────── │
│ 2 小时前更新                                    │ ← 相对时间；V 编号删除；受众并入摘要不再重复
└──────────────────────────────────────────────┘
```

| 要素 | 设计决策 |
|---|---|
| 头像 glyph | 复用信号页 `sv-glyph` 语言：圆角方块 + 名称首字，色相由名称哈希确定性派生，亮/暗主题各一套 |
| 徽章 | 「默认」（品牌色）与「待完善/已完善」（橙/灰）分离共存，语义不再互斥 |
| 完善度 | 4 段小进度条 + `n/4`；与「待完善」状态联动，点击卡片进抽屉即可用 Agent 补齐——把完善动作变成可见目标 |
| 默认账号 | 视觉抬高：品牌色细描边或浅色底，一眼可辨 |
| 页脚 | 只留相对时间；受众信息合并进摘要行逻辑 |
| 卡片交互 | 维持整卡点击进编辑抽屉，不加卡上快捷动作（账号编辑是低频深操作，与信号卡的高频动作分层不同） |

**不做的事**：不加「被几个项目使用」之类的使用统计——需要新增跨项目聚合 RPC，收益配不上改动，留作后续可选。

### 2.3 归档行

归档区保持单行列表形态，仅同步去掉 `v{n}`、改相对时间，不做大改（归档是低频冷区）。

## 4. 待拍板决策点

1. **revision 处置**：A 保留字段仅去显示（推荐）／ B 字段连根删除改用 `updatedAt` 比较。
2. **同步提示文案**：版本不一致时写稿页提示「定位已更新，可重新绑定」是否认可。
3. **卡片重塑范围**：P0 只做「去 V 显示 + 页脚精简」（与问题一联动）；P1 做完整重塑（头像/徽章分离/完善度/默认抬高）。建议 P0+P1 一次做完，改动都集中在 `accountCard` 一个函数。
4. **完善度口径**：定位 4 字段计 4 段（名称为必填不计），还是沿用现有 `configured` 布尔？建议 4 段。
5. **是否先出视觉稿**：可先在 Ardot 里出一版卡片设计稿确认视觉再落代码，或按信号页先例直接落代码 + 截图验收。
